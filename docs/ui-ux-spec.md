> **브랜드:** DevField — `Practice. Solve. Grow.`  
> **문서 버전:** v0.2 (통합 문서 전환 검토안)  
> **기준일:** 2026-10-27  
> **대상 저장소:** `thedevfield/DevField-Web`  
> **권장 저장 위치:** `docs/ui-ux-spec.md` (파일명 고정)  
> **관련 저장소:** `DevField-Auth`, `RepoQ`, `DevField-Platform`  
> **근거:** DevField-Auth Phase 2-A 구현 상태, DevField-Web 초기 구조, DevField-Platform 인증 계약 및 RepoQ PRD  
> **현재 상태:** 화면 기획·설계안. 구현 상태는 저장소 확인과 테스트 결과로 별도 판정한다.

## 1. 목적과 문서 관리 원칙

### 1.1 목적

이 문서는 **DevField-Web의 모든 사용자 화면에 대한 단일 UI/UX 기준 문서(Single Source of Truth)**다. 공통 진입/인증 화면을 시작으로 RepoQ 및 향후 AlgoField·InfraField의 웹 화면을 **같은 파일에 순차적으로 추가**한다.

- 화면 IA, 페이지별 목적·구성·상태·동작, 공통 디자인 시스템, 애니메이션, 반응형 및 접근성 기준을 관리한다.
- 기능을 **Backend → Web BFF → 실제 UI → 브라우저 E2E**까지 완성하는 Vertical Slice 개발을 지원한다.
- 화면마다 별도 `auth-ui-spec.md`, `repoq-ui-spec.md` 등의 **개별 UI 명세 파일을 만들지 않는다**.
- API의 정확한 인증/데이터 계약과 서버 아키텍처는 `DevField-Platform`의 기존 문서를 원본으로 사용한다. 이 파일에는 **화면에 필요한 연동 요약만** 기록하여 문서 중복을 막는다.

### 1.2 문서 갱신 규칙

새로운 기능 화면을 설계하거나 변경할 때는 **아래 항목을 이 파일에서 갱신**한다.

1. **전체 IA/라우트 목록:** 신규 화면의 경로, 진입점, 접근 조건을 추가한다.
2. **페이지별 UI 명세:** 화면 ID를 부여하고 목적·구성·행동·상태·예외·완료 조건을 기입한다.
3. **공통 규칙:** 새로운 UI 패턴이 전체 서비스에서 반복될 때만 디자인 시스템/상태 규칙에 반영한다.
4. **연동·테스트:** BFF/API 의존성과 해당 기능의 E2E 완료 기준을 갱신한다.
5. **변경 이력:** 버전·일자·변경 내용을 기록한다. **기존 화면 ID는 재사용하거나 번호를 바꾸지 않는다.**

**상태 표기 규칙**

| 표기 | 의미 |
| --- | --- |
| `사용자 방향 확정` | 사용자가 원하는 제품/화면 경험에 대해 명시적으로 결정한 범위 |
| `설계 제안` | UI 구성·경로·타이밍 등 제안, 사용자 승인 전 |
| `설계 확정` | 해당 화면의 구조와 동작이 승인된 상태 |
| `구현 완료` | 해당 코드를 실제로 구현했고 구현 결과를 확인한 상태 |
| `E2E 검증 완료` | 실제 브라우저와 Backend 연동으로 정상·주요 예외 흐름을 확인한 상태 |
| `후속 범위` | 요구는 존재하지만 현재 Slice에서는 구현하지 않는 항목 |

> 화면 설계가 끝났다는 이유로 `구현 완료` 또는 `E2E 검증 완료`로 표기하지 않는다. 이후 화면이 늘어나더라도 문서 파일을 분리하거나 기존 내용을 전면 재작성하지 않는다.

### 1.3 화면 ID 규칙

화면 ID는 변경·추가에 영향을 적게 받도록 **도메인 접두사 + 고정 번호**를 사용한다.

| 접두사 | 영역 |
| --- | --- |
| `UI-COM-###` | 공통 Splash, Welcome, 앱 Shell, 공통 탐색 |
| `UI-AUTH-###` | 로그인, 회원가입, 인증, 계정 관리 |
| `UI-REP-###` | RepoQ 프로젝트 분석·연습·면접·이력 |
| `UI-ALG-###` | AlgoField (추후 화면 설계 시) |
| `UI-INF-###` | InfraField (추후 화면 설계 시) |

## 2. 제품 전체 IA 및 사용자 흐름

### 2.1 현재 정의된 라우트

| 화면 ID | 경로(제안) | 화면 | 접근 | UI 상태 | Backend 연동 |
| --- | --- | --- | --- | --- | --- |
| UI-COM-001 | `/` 진입 오버레이 | Splash | 비로그인 초기 진입 | 설계 제안 | 불필요 |
| UI-COM-002 | `/` | Welcome | 비로그인 | 사용자 방향 확정·상세 설계 제안 | 세션 판별 필요 |
| UI-AUTH-001 | `/login` | 로그인 방법 선택 | 비로그인 | 사용자 방향 확정·상세 설계 제안 | 소셜은 후속 |
| UI-AUTH-002 | `/login/email` | 이메일 로그인 | 비로그인 | 설계 제안 | Auth Phase 2-A API 구현됨, Web 미연동 |
| UI-AUTH-003 | `/signup` | 회원가입 방법 선택 | 비로그인 | 사용자 방향 확정·상세 설계 제안 | 소셜은 후속 |
| UI-AUTH-004 | `/signup/email` | 이메일 회원가입 | 비로그인 | 설계 제안 | Auth Phase 2-A API 구현됨, Web 미연동 |
| UI-AUTH-005 | `/signup/check-email` | 이메일 인증 안내 | 비로그인 | 설계 제안 | 가입 결과 상태 필요 |
| UI-AUTH-006 | `/verify-email` | 이메일 인증 결과 | 비로그인 | 설계 제안 | Auth Phase 2-A API 구현됨, Web 미연동 |
| UI-COM-003 | `/app` | 로그인 후 최소 홈 | 로그인 필요 | 설계 제안 | 세션 조회·로그아웃 연동 필요 |

**이후 추가될 영역:** `RepoQ`(프로젝트 등록/분석, 자유연습, 모의면접, 평가/이력), `계정 설정`(소셜 연결, 비밀번호, 탈퇴), `AlgoField`, `InfraField`. 해당 화면의 **정확한 라우트와 구성은 각 기능을 설계할 때 이 표와 본문에 추가**한다. 아직 승인하지 않은 상세 페이지/경로를 미리 확정하지 않는다.

### 2.2 진입/인증 사용자 여정

```text
비로그인 최초 접속
    └─ Splash (DF 로고 드로잉)
         └─ Welcome (요소 순차 등장)
              ├─ 로그인
              │    └─ 로그인 방법 선택
              │         ├─ 이메일 → 이메일 로그인 → /app
              │         ├─ Google → OAuth 로그인 → /app [후속]
              │         ├─ Kakao  → OAuth 로그인 → /app [후속]
              │         └─ GitHub → OAuth 로그인 → /app [후속]
              └─ 회원가입
                   └─ 회원가입 방법 선택
                        ├─ 이메일 → 가입 → 메일 안내 → 메일 링크 인증 → 로그인 → /app
                        ├─ Google → OAuth 가입/로그인 → /app [후속]
                        ├─ Kakao  → OAuth 가입/로그인 → /app [후속]
                        └─ GitHub → OAuth 가입/로그인 → /app [후속]
```

- Splash는 별도 `/splash` 페이지를 만들기보다 **Welcome 진입 오버레이**로 구성하는 방식을 추천한다.
- 로그인 사용자가 `/`·`/login`에 방문하면 서버 측 세션을 검사한 후 `/app` 등 적절한 앱 진입 화면으로 보낸다. 인증 서비스 장애를 단순 로그아웃으로 처리하지 않는다.
- `/app` 및 향후 보호 화면은 **서버 측 접근 제어**를 사용한다. 미인증 사용자는 로그인으로 이동하며, 로그인 뒤 원래 페이지로의 복귀가 필요하다면 **허용된 내부 경로**만 수용한다.
- 모바일과 데스크톱의 화면 진입 순서는 동일하게 유지한다.

## 3. DevField 공통 디자인 시스템

> 색상값은 **제공된 DF 로고의 시각적 인상을 기반으로 한 근사 제안**이다. 원본 자산과 대비율을 점검한 후 확정한다. 로고의 비율·실루엣·색상 조합은 유지한다.

### 3.1 컬러 토큰

| 토큰 | 제안값 | 사용처 |
| --- | --- | --- |
| `--df-navy` | `#04102F` | Splash/Welcome 배경, 딥 네이비 브랜딩 |
| `--df-navy-surface` | `#0B1E42` | 다크 테마의 카드·입력 배경 |
| `--df-white` | `#F0F4FC` | 로고 주변 주요 텍스트 |
| `--df-mint` | `#20DBBA` | Primary CTA, 성공/진행 강조 |
| `--df-sky` | `#47A0FB` | 포커스, 보조 포인트 |
| `--df-muted` | `#B6C5DD` | 안내·보조 텍스트 |
| `--df-error` | `#FF8B96` | 오류 메시지 |

- Splash, Welcome, 초기 인증 화면은 **딥 네이비 중심의 브랜드 경험**으로 설계한다.
- **이후 제품 사용 화면 전체를 다크 테마로 강제하지 않는다.** RepoQ와 다른 훈련 서비스의 화면 목적을 검토해 필요한 표면·배경 토큰을 추가한다. 브랜드 로고/버튼 언어는 일관되게 유지한다.
- Primary 버튼은 민트 배경 + 딥 네이비 글자를 기본으로 하고, Secondary는 아웃라인/네이비 계열을 사용한다.
- Google·Kakao·GitHub 버튼은 동일한 높이·폭과 정렬을 유지하되 실제 공급자 로고는 공식 가이드를 확인한 뒤 적용한다.

### 3.2 레이아웃·타이포·컴포넌트

- **Splash/Welcome:** 100% 뷰포트, 로고와 주요 행동을 중앙 정렬, safe-area 대응.
- **인증 폼:** 데스크톱에서는 최대 너비 약 `420~460px`; 모바일은 단일 컬럼과 좌우 `20~24px` 여백, 긴 폼은 자연스럽게 스크롤.
- **컨트롤:** 입력과 버튼의 권장 높이는 `48~52px`. 모바일 터치 영역, Disabled/Loading/Focus 상태를 정의한다.
- **타이포그래피:** 한국어 가독성이 좋은 Sans Serif와 `system-ui` fallback을 사용한다. 최종 폰트·라이선스는 구현 시 결정한다.
- **공통 컴포넌트 후보:** `BrandLogo`, `PageHeader`, `PrimaryButton`, `SecondaryButton`, `SocialProviderButton`, `FormField`, `PasswordField`, `InlineError`, `StatusView`, `LoadingIndicator`.
- 컴포넌트명과 물리 폴더 구조는 구현 시 기존 코드·라이브러리 점검을 거쳐 확정한다.

### 3.3 공통 상호작용 및 메시지 정책

| 상태 | 화면 처리 |
| --- | --- |
| 기본 | 폼과 CTA 활성. 불필요한 민감 값 보존 금지 |
| 입력 오류 | 해당 필드 가까이에 한국어 문구, 첫 오류로 포커스 이동 |
| 제출 중 | 버튼 내부 진행 상태·중복 제출 방지 |
| 성공 | 완료 메시지와 다음 행동을 명확히 표시 |
| 미인증·세션 만료 (`401`) | 로그인으로 안내하되 Auth 장애와 구분 |
| 이용 불가 (`403`) | 허용되지 않는 계정 상태 안내, 정보 노출 최소화 |
| 만료·소모 (`410`) | 인증 링크의 만료/기사용 안내 |
| 요청 제한 (`429`) | 일시 제한 안내, 자동 재시도 남용 금지 |
| 서비스 장애 (`503`/네트워크) | 실패·재시도 안내, 성공을 거짓 표시하지 않음 |

모든 실제 액션은 키보드로 조작할 수 있어야 한다. 포커스 링, 명시적 `label`, 오류와 입력 연결, `autocomplete`, `prefers-reduced-motion`을 지원한다. 뒤로가기·새로고침·직접 URL 입력에서도 정상 동작해야 한다.

## 4. 애니메이션 및 화면 전환

### 4.1 MOT-001 — Splash 로고 드로잉

| 속성 | 제안 |
| --- | --- |
| 트리거 | 비로그인 사용자의 최초 Welcome 진입 |
| 배경 | `--df-navy` |
| 핵심 요소 | 제공된 **DF 로고 원형 그대로** 중앙 배치 |
| 시각 효과 | 붓이 획을 따라 그리는 듯한 Reveal → 민트·스카이블루 채움 완성 |
| 길이 | 약 `1.4~1.7초`(설계 제안) |
| 종료 | 짧은 Crossfade로 Welcome 등장 |
| 재생 정책 | 같은 탭의 최초 비로그인 진입 1회 재생(제안) |
| 접근성 | 움직임 감소 설정에서는 생략, 사용자 스킵 가능 |

제공된 PNG를 단순히 왼쪽부터 지우개처럼 표시하면 실제 붓 드로잉 효과가 나오지 않는다. **원본 DF 실루엣에 맞는 SVG 경로 또는 마스크 자산**을 준비하는 것을 권장한다. 로고의 형태를 임의로 다시 디자인하지 않는다. 자산 제작이 어려우면 로고 Fade-in을 초기 대체 효과로 사용할 수 있으나, 목표 애니메이션의 완료로 간주하지 않는다.

### 4.2 MOT-002 — Welcome 순차 Fade-up

Splash 종료 후 Welcome 시작 시점을 `t=0ms`로 한다.

| 요소 | 시작 지연 | 지속시간 | 표현 |
| --- | ---: | ---: | --- |
| DF 로고 | `0ms` | `320ms` | opacity + Y `10→0px` |
| 서비스명 `DevField` | `120ms` | `380ms` | opacity + Y `12→0px` |
| 슬로건 | `240ms` | `380ms` | opacity + Y `10→0px` |
| 로그인 버튼 | `400ms` | `340ms` | opacity + Y `10→0px` |
| 회원가입 버튼 | `500ms` | `340ms` | opacity + Y `10→0px` |

- 전체 등장 시간은 약 **840ms**이며, 반복 바운스/강한 Glow 효과는 사용하지 않는다.
- 표시 위치를 처음부터 확보해 레이아웃 점프를 막고 `opacity`·`transform` 위주로 구현한다.
- 버튼은 등장 애니메이션 때문에 불필요하게 조작이 제한되지 않아야 한다.
- `prefers-reduced-motion: reduce`에서는 즉시 모든 요소를 보여준다.
- 이후 일반 화면 이동에서는 과도한 애니메이션을 쓰지 않고 필요한 경우 `150~200ms` 수준의 미세 전환만 사용한다.

## 5. 공통 진입 화면 상세 명세

### UI-COM-001 — Splash

- **경로:** `/` 위 오버레이(독립 라우트 아님, 제안).
- **목적:** 브랜드 DF 로고의 첫 노출을 짧고 인상적으로 제공.
- **구성:** 전체 딥 네이비 배경, 가운데 DF 로고, 스킵 제어(필요 시).
- **상태:** `재생 중 → 종료 중 → Welcome` / `건너뜀 → Welcome` / `Reduced Motion → Welcome`.
- **완료 기준:** 로고 비율·색상 보존, 브라우저 탭 반복 방문 시 정책 준수, 전환 중 깜빡임·무한 로딩 없음.

### UI-COM-002 — Welcome

- **경로:** `/`.
- **목적:** 브랜드 메시지와 로그인·회원가입 진입 제공.
- **구성:** `DF 로고 → DevField → Practice. Solve. Grow. → 로그인 → 회원가입` 순서.
- **Primary:** `로그인` → `/login`.
- **Secondary:** `회원가입` → `/signup`.
- **모션:** `MOT-002`에 정의된 순차 Fade-up.
- **인증 상태:** 이미 로그인한 사용자는 검증 후 `/app`으로 이동. Auth 실패는 자동 로그아웃과 구분.
- **완료 기준:** 모든 요소가 순서대로 등장하고 모바일·데스크톱, 키보드 조작, 스킵/Reduced Motion에서도 사용 가능.

```text
               [ DF 로고 ]

                 DevField
          Practice. Solve. Grow.

               [ 로그인 ]
               [ 회원가입 ]
```

### UI-COM-003 — 로그인 후 최소 홈

- **경로:** `/app`.
- **목적:** 공통 인증이 실제로 동작함을 확인하고 후속 제품 경험의 진입점 제공.
- **구성:** 공통 헤더(DF/DevField), 간단한 환영 메시지, 향후 RepoQ 영역 진입 자리, 로그아웃 액션.
- **주의:** 프로젝트 목록·면접 결과·사용자 표시 이름 등 아직 제공되지 않는 데이터는 꾸며서 노출하지 않는다.
- **접근 제어:** 서버 측에서 세션 유효성을 확인한 뒤 렌더링. 만료/폐기 세션은 로그인으로, Auth 장애는 재시도 가능한 오류 상태로 분기.
- **로그아웃:** BFF를 통해 Auth 세션을 폐기한 뒤 Web Cookie 정리. 서버 폐기 실패 시 성공으로 표기하지 않는다.
- **범위:** 현 단계는 최소 앱 홈만 구현. 제품 Dashboard와 실제 메뉴는 해당 서비스 Slice 설계 시 이 파일에 추가.

## 6. 인증 화면 상세 명세

### UI-AUTH-001 — 로그인 방법 선택

- **경로:** `/login`.
- **제목:** `로그인` / **설명:** `DevField에 로그인할 방법을 선택해주세요.`
- **방법:** `이메일로 로그인`, `Google로 계속하기`, `Kakao로 계속하기`, `GitHub로 계속하기`.
- **동작:** 이메일 → `/login/email`; 소셜은 실제 OAuth 구현 후 각각 Auth 승인 흐름 시작.
- **보조 탐색:** 뒤로가기 → `/`, `계정이 없나요? 회원가입` → `/signup`.
- **미구현 UX:** 개발 디자인 프리뷰에는 `준비 중` 비활성 표기를 허용하되, 미구현 버튼을 작동하는 로그인처럼 배포하지 않는다.

### UI-AUTH-002 — 이메일 로그인

- **경로:** `/login/email`.
- **제목:** `이메일로 로그인`.
- **입력:** 이메일, 비밀번호(표시/숨김).
- **Primary:** `로그인`; 제출 중 비활성/진행 표시.
- **동작:** 브라우저 → Web BFF → 기존 Auth `POST /api/auth/login`; BFF는 반환받은 `sessionHandle`을 서버 측에서만 이용해 HttpOnly Cookie를 설정 → `/app`.
- **오류:** 유효하지 않은 입력, `401` 자격 불일치, `403` 계정 이용 불가, `429` 제한, `503` 장애. 개인정보/계정 존재 여부를 필요 이상 노출하지 않는다.
- **보조 탐색:** `/login`으로 뒤로가기, 회원가입 이동. 비밀번호 재설정 링크는 해당 Backend가 구현된 뒤 활성화.
- **완료 기준:** 로그인 성공, 오입력, 이메일 미인증, 새로고침/세션 유지, 중복 제출 방지가 브라우저에서 검증됨.

### UI-AUTH-003 — 회원가입 방법 선택

- **경로:** `/signup`.
- **제목:** `회원가입` / **설명:** `DevField를 시작할 방법을 선택해주세요.`
- **방법:** `이메일로 회원가입`, `Google로 계속하기`, `Kakao로 계속하기`, `GitHub로 계속하기`.
- **동작:** 이메일 → `/signup/email`; 소셜 로그인/가입은 제공자별 동일 OAuth 기반으로 처리하되 진입 목적은 구분.
- **보조 탐색:** 뒤로가기 → `/`, `이미 계정이 있나요? 로그인` → `/login`.
- **계정 정책:** 같은 이메일이라는 이유로 기존 소셜/이메일 계정을 자동 병합하지 않는다.

### UI-AUTH-004 — 이메일 회원가입

- **경로:** `/signup/email`.
- **제목:** `이메일로 회원가입`.
- **입력:** 표시 이름, 이메일, 비밀번호, 비밀번호 확인.
- **검증:** 현재 Auth 구현 기준 표시 이름 공백 불가·100자 이하, 비밀번호 12~256자, 이메일 형식. 비밀번호 확인은 Web에서만 비교하고 Auth에는 전송하지 않는다.
- **Primary:** `회원가입` → Web BFF → Auth `POST /api/auth/signup`.
- **성공:** `202 verification_required` → `/signup/check-email`. 이 응답은 계정 존재·실제 메일 발송 여부를 공개적으로 보증하지 않으므로 화면 문구도 이를 반영한다.
- **오류:** 입력 오류(400), 요청 제한(429), 메일/서버 장애(503)를 구분한다.
- **보안:** 비밀번호/이메일을 URL Query에 포함하지 않는다. 약관/개인정보 처리방침과 동의 UI는 실제 서비스 오픈 전에 정책·링크를 확정한다.

### UI-AUTH-005 — 이메일 인증 안내

- **경로:** `/signup/check-email`.
- **제목:** `이메일을 확인해주세요`.
- **안내:** `입력하신 주소로 가입 인증이 가능한 경우 안내 메일이 발송됩니다. 메일함과 스팸함을 확인해주세요.`
- **Primary:** `로그인으로 이동` → `/login/email`.
- **제외:** 현재 Auth에 재발송 전용 API가 없으므로 재발송 버튼을 구현하지 않는다.
- **예외:** 직접 경로 진입·새로고침에도 개인정보 없이 자연스러운 안내를 표시한다.

### UI-AUTH-006 — 이메일 인증 처리/결과

- **경로:** `/verify-email`; 메일 링크는 `/verify-email#token=<일회용 증명>` 형태.
- **처리:** Web이 Fragment의 토큰을 클라이언트 메모리에서 읽은 직후 `history.replaceState`로 URL에서 제거 → BFF `POST /api/auth/verify-email` → Auth의 같은 경로로 전달.
- **상태:** 검증 중 / 인증 성공 / 링크 만료·소모(410) / 형식 오류(400) / 서버 장애(503).
- **성공 메시지:** `이메일 인증이 완료되었습니다.` + `로그인하기` → `/login/email`.
- **만료 메시지:** `인증 링크가 만료되었거나 이미 사용되었습니다.`; 재발송 불가 상태에 맞게 가입 화면으로 안내.
- **보안:** 증명 원문을 로그·분석 도구·오류 메시지·서버 URL Query에 노출하지 않는다. 화면 재렌더에 의한 중복 제출을 막는다.
- **완료 기준:** 실제 메일 링크, 성공/이미 사용된 링크/만료/잘못된 링크/네트워크 오류에 대한 브라우저 검증.

## 7. 인증 Web BFF ↔ Backend 연동

### 7.1 현재 API 연결 계획

| Web BFF 새 API(제안) | Auth 기존 API(구현됨) | 사용 화면 |
| --- | --- | --- |
| `POST /api/auth/signup` | `POST /api/auth/signup` | UI-AUTH-004 |
| `POST /api/auth/verify-email` | `POST /api/auth/verify-email` | UI-AUTH-006 |
| `POST /api/auth/login` | `POST /api/auth/login` | UI-AUTH-002 |
| `POST /api/auth/logout` | `POST /api/auth/logout` | UI-COM-003 |
| `GET /api/auth/session` (신규 Web 제안) | `POST /internal/auth/session-token` 등 BFF 허용 세션 경로 사용 검토 | UI-COM-002·003 및 보호 라우트 |

- Auth의 `GET /api/auth/jwks`는 Project/Interview JWT 검증용 공개 API다. 일반 로그인 화면에서 호출하지 않는다.
- Auth의 `POST /internal/auth/session-check`는 **Project/Interview 용도**이며 Web BFF가 임의로 사용하는 API가 아니다.
- BFF 세션 판별 방식과 호출 빈도는 Phase 2-B 사전점검에서 검증한다.

### 7.2 변하지 않는 보안 규칙

- 브라우저는 **같은 출처 Web BFF API**에만 인증 요청을 보낸다.
- BFF의 Auth 서비스 인증 키, 사용자 JWT, 세션 핸들은 **브라우저 JavaScript/응답 본문/localStorage**에 노출하지 않는다. Web Cookie에만 불투명 핸들을 `HttpOnly`로 저장한다.
- Cookie는 host-only, HTTPS 운영 환경에서 `Secure`, 적절한 `SameSite`와 수명·삭제 규칙을 적용한다. 정확한 운영 값은 도메인/배포 정책 확정 후 결정한다.
- Cookie가 적용되는 상태 변경 요청에는 **Origin 검증 + CSRF 증명**을 적용한다. 세부 증명 전달 방식은 구현 전 점검한다.
- 브라우저가 보낸 서비스 인증 관련 임의 헤더·사용자 ID·JWT는 신뢰하여 그대로 업스트림에 전달하지 않는다.
- `401` 미인증, `403` 권한/계정 상태, `410` 일회용 증명 만료, `429` 남용 제한, `503` 서비스 장애를 구분한다.
- 회원 탈퇴·연결 해제·OAuth 계정 연결은 별도 보안 검토가 필요한 후속 화면이며 이 Slice에서 구현 완료로 표시하지 않는다.

### 7.3 소셜 로그인/회원가입 후속 적용

- 정식 지원 제공자: **Google / Kakao / GitHub**.
- 회원가입 버튼에서 시작했더라도 이미 해당 제공자로 등록된 계정이면 재로그인으로 연결될 수 있다.
- 동일 이메일만으로 서로 다른 사용자 계정을 자동 병합하지 않는다.
- 기존 계정에 다른 소셜 수단을 추가/해제하는 기능은 **계정 설정 영역**에서 명시적 본인 확인 후 수행한다.
- OAuth `state`, 브라우저 결합, 일회용 handoff, 제공자 취소/거부, 충돌, 재생 공격 방어 및 실제 콜백 E2E를 별도 Slice에서 검증한다.
- **현재 Auth Phase 2-A에는 OAuth API가 없다.** 화면 설계와 실제 로그인 가능 상태를 혼동하지 않는다.

- [ ] Splash와 Welcome이 로고 및 등장 순서를 올바르게 표시하며 Skip/Reduced Motion을 지원한다.
- [ ] 로그인/회원가입 분기가 맞고 이메일 상세 화면으로 이동한다.

- [ ] 로그인 세션 핸들이 JavaScript에 노출되지 않고 HttpOnly Cookie로 유지된다.
- [ ] 새로고침·직접 접근 시 서버 측 세션 검사와 접근 제어가 올바르다.
- [ ] 로그아웃 성공 후 Auth 세션 폐기·Cookie 삭제·보호 화면 차단이 확인된다.
- [ ] CSRF·Origin 검증, 오류/장애 상태, 비밀 값 로그 노출 방지를 검증한다.

비밀번호 재설정·변경, Google/Kakao/GitHub 계정 연결/해제, 프로필·계정 설정, 회원 탈퇴 진행/완료 화면을 각각의 Backend 기능 개발 때 추가한다. 마지막 로그인 수단 해제 방지와 분산 데이터 삭제 정책은 기존 Auth 계약을 따른다.

### 9.3 AlgoField·InfraField — 후속 설계 영역

각 제품 구현 시 **동일 문서에** `UI-ALG-###`, `UI-INF-###` 화면 상세와 사용자 흐름을 추가한다. 공통 탐색/UI 컴포넌트를 재사용하되 두 서비스가 RepoQ 선행 이용을 요구하는 흐름은 만들지 않는다.

### 9.4 새 화면 작성 템플릿

아래 블록을 **같은 파일의 해당 제품 영역**에 추가한다. 새 문서를 만들지 않는다.

```md
### UI-REP-001 — [화면명]

- **상태:** 설계 제안 / 설계 확정 / 구현 완료 / E2E 검증 완료
- **경로:** [라우트, 미정이면 제안 표시]
- **사용자 목적:** [이 화면에서 하려는 일]
- **진입·이탈:** [어디서 오고 어디로 가는지]
- **접근 조건:** [로그인, 소유권, 권한 등]
- **레이아웃:** [헤더/사이드바/본문/모바일 변화]
- **주요 UI 요소:** [데이터/입력/버튼/메시지]
- **행동·상태:** [초기/로딩/빈 결과/성공/실패/재시도]
- **API/BFF 의존성:** [기존 계약 참조, 신규 계약은 확정 전 표기]
- **완료 기준:** [브라우저 E2E·접근성·보안 등]
```

화면마다 필요한 항목만 구체화한다. 공통 디자인 토큰, OAuth 보안 규칙, 동일한 상태 메시지를 각 화면에 장문 반복하지 않는다.

## 10. 현재 남은 설계 결정

| 항목 | 현재 권장 방향 | 상태 |
| --- | --- | --- |
| Splash 노출 빈도 | 비로그인 탭 세션 첫 진입 1회 | 설계 제안 |
| Splash 그리기 방식 | 원본 DF 형태를 유지하는 SVG/마스크 | 설계 제안 |
| Splash 길이 | 1.4~1.7초 | 설계 제안 |
| Welcome 등장 | 0.84초 이내 순차 Fade-up | 사용자 방향 확정·수치 제안 |
| Splash 라우트 | `/` 오버레이 | 설계 제안 |
| 로그인·가입 선택 | 서로 다른 화면에서 4가지 방법 선택 | 사용자 방향 확정 |
| 미구현 소셜 버튼 | 프리뷰만 비활성/준비 중, 배포 시 오인 방지 | 설계 제안 |
| 구현용 UI/CSS 도구 | 기존 Web 코드 확인 후 선정 | 미정 |
| 실서비스 Cookie·CSRF 정책 | 보안·배포 도메인 점검 후 확정 | 미정 |
| 인증 후 상세 서비스 대시보드 | 해당 제품 Slice에서 추가 | 후속 범위 |
